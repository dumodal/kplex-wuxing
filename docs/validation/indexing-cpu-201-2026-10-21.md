# Indexing CPU work — PR #201

Safe partial implementation on `2026-10-21-indexing-cpu-reduction`, from
`0c9416667c441c1ee9d3b064c7ca1500672e0a0a`. Runtime baseline is the accepted PR base
`551a3b5`; the intervening branch commits contain the handoff only. The local `main`
release metadata at `a233338` was not folded into this implementation. No release is prepared.

The 50% end-to-end CPU target is **not met**: the final matched Small-vault observations show
6.21% lower median reconstruction CPU and 15.30% higher median warm-restore CPU to equivalent
closure. Correctness verification passes; this is not general performance acceptance. All changes
remain uncommitted, and the draft PR is unchanged.

## Confirmed mechanisms and changes

1. A dormant initial `create` notification set one global flag that retained all pre-restore
   reasons, even after a fresh snapshot captured the same native identities and physical tree.
   A folder/attachment `vault:create` reason selected a full rebuild. The coordinator now retires
   only fresh, pre-capture create observations whose native identity, path and file statistics
   still match. Dormant edits/destructive events and unknown, stale or later input remain queued.
   The existing `finishStartupIndexPreparation()` scheduling obligation is unchanged.
2. Full rebuilding intentionally leaves neutral source acquisition for later. It cached a complete
   parse, but acquisition's body-dirty state rejected that cache. Independent URL discovery also
   discarded the complete parse after projecting URLs. Exact current-process input tokens now
   travel with complete hot/queued/durable parser records. Dirty state remains dirty; a token
   authorizes only optional parser-input reuse, never a source head, resolution, coverage or edit.
   Pure parser validity uses native identity/path/statistics/per-file observations. Semantic/source
   work additionally retains its original host, caller, generation and publication fences.
3. A missing durable source head creates a synthetic incarnation fence during inventory. A complete
   current-process parse can cross that specific synchronous fence while dirty/created state and
   semantic cancellation remain intact. Old unqualified path/mtime bodies cannot cross it.
4. A second sharing checkpoint publishes each completed full-build parse into the existing hot
   field cache immediately, before the group yields. Before submitting another full-build parse,
   the existing priority checkpoint now runs, then the original input epoch, native file and caller
   fences are rechecked. An exact completed-token hot/queued peek can reuse work completed during
   that suspension without a database wait or joining another task. An accepted receipt's delayed
   writer additionally requires that exact receipt to remain selected and unretired; an older
   writer cannot replace a newer completed token. These changes grant lexical input reuse only:
   graph publication and neutral-source authority remain unchanged.

The existing body queue now has count and estimated-payload budgets: desktop 1,200 / 32 MiB,
mobile 160 / 8 MiB, iOS 48 / 4 MiB. Eviction removes only optional acceleration. One existing
in-flight bounded batch may additionally retain retired queue entries. Estimates describe parser
DTO payloads, not raw Markdown or actual process peak memory. There is no extra body collection,
new source store, schema upgrade, worker pool, scheduling policy or foreground durability wait.

The body-cache version now derives from the canonical parser version; both already equal 3 on the
baseline. Database version is unchanged. This assignment introduces no numeric cache-version bump
or forced first-upgrade invalidation; existing unqualified clean hits retain their established contract.

The second checkpoint follows three deliberately failing characterizations retained privately:
`kplex-pr201-hot-sharing-before.log` observed two parses instead of one before the group yield;
`kplex-pr201-admission-sharing-before.log` observed a P4 parser submission while P3 remained held;
`kplex-pr201-selected-receipt-before.log` observed a superseded queued writer forcing a third native
read. After the repair, the focused 79-case group, four real-IndexedDB cases, production indexing
harness, TypeScript and official ESLint checks pass. These focused results establish the named
input-sharing/race contracts, not an end-to-end CPU gain. Complete `final8` verification now passes
for this checkpoint, as recorded below. Its twelve native v2 comparisons now complete successfully;
they are reported separately from the earlier checkpoint measurements below.
